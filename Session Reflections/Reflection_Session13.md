## 2. Faculty Guidance on Git Discipline

The faculty's check-ins this session focused on *how* teams were working, not just *what* they had built — specifically, whether groups were pushing to GitHub regularly and following practices that avoid merge conflicts while working independently on separate branches.

> [!TIP]
> **The Core Advice:**  
> Commit often, push before pulling, and communicate before touching shared files. These aren't new principles, but they matter more once a team is working in parallel without being in the same room.

---

## 3. Cross-Platform Verification

Before any new planning, the group confirmed the project actually ran on every team member's machine — three on Windows, one on Mac.

> [!IMPORTANT]
> **Why This Check Matters:**  
> A cross-platform check is easy to skip when development started on a single machine, but it can hide path issues, font rendering differences, and JavaFX behavior quirks that only surface on a different OS. Once confirmed working on both platforms, the team moved on to planning.

# Key Takeaways

1. **Cross-Platform Checks Come First:** Verifying the app runs on every team member's OS before planning new features catches hidden path and rendering issues early.
2. **Dark Mode and Drag-and-Drop Are Expected, Not Extra:** Both are standard in mature desktop applications and were chosen for genuine usability, not just polish.
3. **Git Discipline Is a Team Practice:** Committing often, pushing before pulling, and communicating before touching shared files prevents most merge conflicts in a parallel-branch workflow.
4. **UI Direction Is a Deliberate Decision:** Moving from a default look to a tech-themed aesthetic was planned explicitly, not left to happen incidentally during implementation.
5. **Plan Around Known Constraints:** Scheduling ideation before an exam period, with implementation deferred, keeps project momentum without competing against study time.

## Final Reflection

Session 13 reinforced that project work isn't only about writing code - a session can be entirely planning and verification and still move the project forward meaningfully. Confirming Taskwood ran correctly on a teammate's Mac felt like a small step, but it's the kind of check that prevents a much bigger problem later if skipped. Deciding on dark mode, drag-and-drop, and a UI refresh before touching any code also meant the team walked away with clear, individually owned tasks rather than a vague direction - which matters even more heading into an exam period where the team's pace will necessarily slow down.
